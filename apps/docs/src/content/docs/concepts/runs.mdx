## Runs

A **run** is one task for an agent: an input in, a model's answer out, with any tool calls in between.

```ts
const run = await zupflow.runs.create(workspaceId, agentId, { input: "What's due this week?" });
```

A run's `status` moves through:

```mermaid
stateDiagram-v2
    direction LR
    [*] --> queued
    queued --> running
    running --> waiting_for_approval: a call needs approval
    waiting_for_approval --> running: decided
    running --> completed
    running --> failed
    queued --> cancelled
    running --> cancelled
    waiting_for_approval --> cancelled
    completed --> [*]
    failed --> [*]
    cancelled --> [*]
```

The run records its model and connection when it starts, and checks before every model call that both are still there. With neither an agent model nor an environment default, starting a run is refused (`422 model_not_configured`).

## Events

Every step is an event with a `sequence` number. Read them all, or only those after a sequence you already have:

```ts
const events = await zupflow.runs.events(workspaceId, run.id, lastSequence);
```

| Event | When |
| --- | --- |
| `run.queued`, `run.started` | Admitted, then taken up with its model. |
| `message.assistant` | The model said something. |
| `tool_call.started`, `tool_call.completed`, `tool_call.failed` | A call was sent and answered. |
| `approval.requested`, `approval.resolved` | A call waits for a decision, then gets one. |
| `run.completed`, `run.failed`, `run.cancelled` | The run ended. |

## Approvals

When a call needs approval, the run pauses with `waiting_for_approval`, records `approval.requested` with the call's ID and arguments, and Zupflow sends the `run.waiting_for_approval` webhook. Your product shows the person what the agent wants to do; your backend sends the decision:

```ts
await zupflow.runs.resolveApproval(workspaceId, runId, {
  call_id: callId,
  decision: "denied",
  reason: "Not this week.", // optional, goes back to the model
});
```

- **Only an API key can decide.** A Console session gets `403 approval_requires_api_key`: the Console observes approvals, the person decides in your product.
- A denial's `reason` goes back to the model as the call's result, so it can carry on without the call.
- Deleting or disconnecting the installation refuses its waiting calls, so the run goes on without anyone deciding. Deleting a memory type does the same for the memory calls waiting in it. A decision sent after that answers `409 not_waiting`.

## Memory

A run starts with its agent's [memory](/concepts/memory/): it recalls what the agent remembers in the workspace, and the agent's memory tools join its tools. The recall is read once, before the first model call, and stays the same for the whole run. What the run saves reaches the next one.

Start a run with `memory: "off"` to leave memory out of it. It recalls nothing, and every call to a memory tool is refused; the tools stay offered, so its prompt is the same as any other run's. A run's `memory` says how it started: `agent` (the default) or `off`.

```ts
const run = await zupflow.runs.create(workspaceId, agentId, {
  input,
  memory: "off",
});
```

Memory calls are on the timeline like any call. Their `tool_call.*` and `approval.requested` events name the memory type (`memory_type_id`, `memory_type_name` and `kind`) where an app's call names its installation, and a write that needs approval is decided like any other. A memory call that isn't made fails with a code that says why, and the run goes on:

| `error.code` | Why |
| --- | --- |
| `memory_off` | The run was started with `memory: "off"`. |
| `memory_type_removed` | The run's memory type was deleted. |
| `memory_kind_not_served` | This server doesn't serve the type's kind. |
| `invalid_memory_settings` | The type holds settings its kind refuses now. |
| `tool_refused` | The type's `writes` is `deny` now: the memory is read-only. |
| `memory_unavailable` | The memory couldn't be reached just now. Nothing changed. |

## Cancelling

`POST /v1/workspaces/{ws}/runs/{run}/cancel` stops a run and closes every call not yet sent.

## Durability

Runs survive interruptions. Each step is saved before it's taken, and a call whose outcome was lost mid-send is settled as **unknown**, never sent again. A memory call that changed a memory but lost its answer is answered from the record saved with the change, so the change is never made twice. A run nothing can take forward any more fails with `run_unavailable`.
